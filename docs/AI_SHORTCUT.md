# One-step AI meal import (v1.30.0)

`POST /json-import` saves one whole consumed meal directly to the diary. Authentication: `Authorization: Bearer YOUR_FRISS_API_KEY`; JSON body (`Content-Type: application/json`). The existing `/json-import/preview` and `/json-import/commit` remain available for the browser and older clients; they use their existing per-100-g/ml format. Do not send the new format there.

## iPhone Shortcut

1. Collect your description and optionally a photo. Keep your original description in a variable.
2. Choose the meal date/time in the Shortcut and format it as **ISO 8601 with timezone**. This is the time the meal is logged, not the model's generation time.
3. Give the model the prompt in [AI_PROMPT_DE.txt](AI_PROMPT_DE.txt), your description and optional photo. Keep the answer as text.
4. **Get Contents of URL**: `http://spiesserver:8001/json-import`, method **POST**. Use your actual Friss address if different. Set the Authorization header above and request body **JSON**, with only three fields:

| Field | Type in Shortcuts | Value |
| --- | --- | --- |
| `timestamp` | Text | Chosen date formatted as ISO 8601 |
| `original_message` | Text | Original user description |
| `ai` | Text | Model's complete response variable |

Shortcuts serializes/escapes that text automatically. No manual brackets, dictionary extraction, UUID generation, repeated nutrient list, preview or commit call. Optionally show the response with Quick Look. HTTP 201 and `status: completed` means saved; `entry_ids` identifies the diary entry. A 422 error means the input was rejected, not saved. AI JSON syntax errors report line/column. The API also accepts `ai` as a JSON object if another client already parses it. Markdown fences around AI text are tolerated.

## Meaning and storage

- `ai.title`: short meal name; required.
- `ai.nutrients`: **totals for the entire consumed amount**, not per 100 g/ml. At least one known nutrient is required. Never multiply the model's totals by portion weight in the Shortcut.
- `ai.quantity`: optional positive `{value, unit}` in g/ml. It describes the consumed amount and is retained. Unknown quantity may be omitted/null: supplied totals are still saved. Do not invent a conversion between ml and g.
- `ai.estimated`: defaults to true; false only for reliable measured/label values.
- `ai.notes`: optional assumptions/uncertainty, max 2,000 characters. Original description max 10,000 characters. Whole request max 256 KiB.
- Unknown nutrients remain unknown (omit/null); zero means an actual zero. Only existing Friss/HealthKit nutrient identifiers and compatible units are accepted. µg, μg and ug are normalized to mcg internally. No database lookup or additional AI call takes place.
- One diary entry is created for the whole meal, so ingredients must not also be booked separately. The original AI response and Shortcut metadata are archived under `data/originals/request-<id>.json`, with normal diary originals beside it. The original description is also in entry import metadata. Photos themselves are not uploaded by this JSON endpoint; from v1.33.0 the separate `/entries/{id}/photos` endpoint below attaches them.
- With a known original quantity, later reprocessing after a quantity change scales the totals relative to that quantity. Without one, the imported totals remain absolute.
- IDs are generated by Friss from the complete request. Retrying an **identical request** returns the same batch and entry, preventing duplicates. Keep timestamp, original message and AI text unchanged on retry; do not rerun the model or use a new current time. Changing them creates a new import. This is not an update endpoint; correcting a saved meal requires editing/deleting it in Friss. A deleted import cannot be recreated by retrying the same request.
- Saves locally in Friss; Apple Health transfer remains a separate step. Estimates are labelled and not independently verified by Friss.

## Example request

See [examples/ai-meal.json](examples/ai-meal.json). That example's 500 g meal contributes **775 kcal**, **97.5 g carbohydrates**, **37.5 g protein**, **25 g fat**, **10 g fibre**. Values are illustrative estimates.

```sh
curl http://spiesserver:8001/json-import \
  -H 'Authorization: Bearer YOUR_FRISS_API_KEY' \
  -H 'Content-Type: application/json' \
  --data-binary @docs/examples/ai-meal.json
```

For Shortcuts choose `ai` type **Text** and insert the model-response variable instead of creating the nested example object by hand.

## Upload the photos too (v1.33.0)

The AI prompt and the three-field meal request stay unchanged. Send the images directly to Friss **after** the meal import succeeds, as separate binary file requests. No base64 and no image data in the model's JSON are needed.

1. Keep the picture(s) given to the model in a Shortcut variable, e.g. **Meal photos**. For HEIC, use **Convert Image → JPEG** before sending to the model and keep that converted image for upload. Friss accepts static JPEG, PNG and WebP, not HEIC.
2. Run the existing `POST /json-import` action and keep its response as **Friss response**. Check `status` is `completed` before continuing.
3. Use **Get Dictionary Value → entry_id** from **Friss response**, then **Set Variable → Friss entry ID**. The server now returns this singular ID in addition to the existing `entry_ids` list. It also returns the relative `photo_upload_url`.
4. Add **Get Contents of URL**:

   URL: `http://spiesserver:8001/entries/` + **Friss entry ID** variable + `/photos`

   - Method: **PUT**
   - Header `Authorization`: `Bearer YOUR_FRISS_API_KEY`
   - Header `Content-Type`: `image/jpeg` (or `image/png` / `image/webp` for those formats)
   - Request Body: **File**, using the actual image variable. Do not choose JSON or Form and do not paste a filename/base64 text.
5. For multiple photos, put step 4 inside **Repeat with Each** over **Meal photos**, passing the **Repeat Item** image as File. All photos use the same entry ID and URL. Skip the loop for a text-only meal with no photos.

An HTTP 200 upload response contains the photo's `id`, `url`, `size` and `content_type`. In Friss open the meal: **Original photos / Originalfotos** shows the images; tap one to open its full original. Uploads are authenticated and only stored locally on your server; Friss does not send them to a model.

### Retry and storage

- The meal is already saved before its photos are sent. A failed upload does **not** undo the meal. Keep the entry ID and retry the photo upload, rather than asking the model again or creating another meal.
- Uploading the same file bytes to the same entry again returns the same photo ID without making a duplicate. Different files become additional photos, up to 20 per entry. Re-encoding an image changes its bytes, so it may count as a new photo; retain the converted file for retries.
- Maximum 15 MiB and 40 megapixels per image. File contents are decoded/validated; changing a filename or Content-Type does not make HEIC or a non-image acceptable.
- Submitted bytes (including any embedded metadata) are preserved in `data/originals/<entry-id>-photo-<sha256>.<jpeg|png|webp>`. Friss does not recompress or overwrite them. The Shortcut's HEIC-to-JPEG conversion happens before upload; the HEIC source itself is not archived by this API.
- Photos do not alter nutrients, timestamps, revisions, BAC or Health export status. They are included automatically in ZIP backups. Entry copies and recipe duplicates copy photos present at that time. Later additions are not propagated to old copies.
- Original-file retention follows existing Friss behavior: deleting an entry removes its API access but leaves its original files on disk and in later backups.
- The older `PUT /entries/{id}/photo` JPEG endpoint for photo-capture entries remains unchanged; for AI imports use the plural `/photos` endpoint documented here.

### API example

Use the `entry_id` returned by your meal request in this URL:

```sh
curl -X PUT 'http://spiesserver:8001/entries/ENTRY_ID_FROM_MEAL_RESPONSE/photos' \
  -H 'Authorization: Bearer YOUR_FRISS_API_KEY' \
  -H 'Content-Type: image/jpeg' \
  --data-binary @meal.jpg
```

`GET /entries/{id}/photos` lists that entry's photos. `GET /entries/{id}/photos/{photo-id}` retrieves the original binary file. Both require the same authentication as the upload. The regular entry details response also contains a `photos` list.
